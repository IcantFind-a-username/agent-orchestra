# 设计说明

本文只描述可复用底座的设计，不含任何具体部署、账号或厂商配置。

## 1. 目标与非目标

**目标**：一个可嵌入、可审计、可恢复的多模型任务编排内核。给定一句话需求，
在无人值守的情况下产出可审查的代码改动，并且全过程留下可核对的证据。

**非目标**：

- 不是一个通用 agent 框架（不提供工具沙箱给模型自由调用）
- 不是多租户服务（单用户、单机、回环）
- 不做任意语言的自主编程（先约束在可沙箱验证的子集）

## 2. 三个关键设计选择

### 2.1 为什么是持久状态机，而不是一次函数调用

一次函数调用式 agent 的问题不在能力，在**可恢复性**：进程被杀、网络断开、模型超时，
状态就没了，重试意味着重跑并重复付费。把任务、阶段、产物、事件落进 SQLite 后：

- 重启后可以只恢复未完成阶段
- 每次状态变化有事件记录，可回放
- 并发写入用租约（lease）+ run token 防护，陈旧调用不会覆盖新状态

租约机制的价值在于：即使一个 worker 卡死，它的写入也会因为 token 不匹配被丢弃，
而不是把任务推进到错误状态。

### 2.2 为什么强制实现端与审查端是不同厂商

同一个模型审查自己的输出，存在系统性自我确认偏差：它会倾向于认可自己的选择，
而不是重新审视。把审查交给另一个厂商的模型，能显著降低这种相关性错误。

代价是成本和复杂度上升，以及需要处理「审查方不认可实现方」的僵局——
这部分交给固定的失败语义（见 §7），而不是自动重试到通过。**审查不通过就是一次真实信号**，
用重试把它磨掉等于取消了这个机制。

**为什么这件事值得做：复核的边际成本决定它是否会发生。** 单看账单，很少有人愿意为
「让另一个模型复核一遍」额外付一份费用——审查的收益是概率性的，成本是确定的，
理性选择往往是不审。但如果用户已经配置了多个端点，把同一个需求再交给另一家跑一遍，
增量开销很低。

这是本设计的前提：**独立审查的可负担程度，取决于用户已经拥有几个端点。**
端点越多，复核越接近默认配置；只有一个时，这套编排会退化成「同一模型自审」，
主要意义随之消失。这也是内核强制要求实现端与审查端必须不同、而不是允许配成同一个的原因。

### 2.3 为什么固定五阶段而不是动态 DAG

固定阶段牺牲了灵活性，换来三个性质：

- 每个阶段有明确的输入输出契约，可单独测试
- 每个阶段结束时留下可比对的证据（提交 SHA、审查意见、测试报告）
- 「任务完成」有唯一判定标准，不需要推理图的可达性

动态 DAG 会让「这个任务到底做完了没有」变成一个需要解释的问题。对审计场景来说，
可解释性比表达力重要。

## 3. 领域模型

| 实体 | 作用 | 关键字段 |
|---|---|---|
| `Task` | 一次需求 | `request_id`（幂等键）、`status`、`stage`、`revision`、`policy`（不可变快照） |
| `Step` | 一个阶段的执行记录 | `stage`、`status`、`provider`、`model`、`revision`、`summary` |
| `Approval` | 一次待批操作 | `operation`（人读）、`operation_digest`（绑定用）、`status` |
| `Artifact` | 阶段产物 | `name`、`content`（文件内容、diff、审查 JSON） |
| `Event` | 追加型审计日志 | `seq`（递增）、`kind`、`at`、`data` |

`revision` 是贯穿全局的版本锚点：审查针对它、审批绑定它、测试报告记录它。
任何一次新的提交都会让旧的审查与审批失效。

## 4. 状态机

```
                 submit
                   │
                   ▼
    ┌──────────► queued ◄──────────┐
    │              │               │
    │           claim              │ resume
    │              ▼               │
    │           running ───────────┤
    │              │               │
    │      ┌───────┴────────┐      │
    │      ▼                ▼      │
    │  stage_done      waiting_approval
    │      │                │      │
    │      │            approve     │
    │      ▼                ▼      │
    │   next stage ────► queued    │
    │      │                       │
    │      ▼                       │
    │  completed                   │
    │                              │
    └── paused / rate_limited / quota_exhausted / auth_required / timed_out
```

- **终态**：`completed`、`failed`、`cancelled`
- **可恢复**：`paused`、`rate_limited`、`quota_exhausted`、`auth_required`、`timed_out`
- **暂停语义**：暂停一个真实执行中的任务会保留已完成阶段的产物，恢复时从当前阶段继续

状态转移只允许发生在控制器内部。适配器、HTTP 层、客户端都无权直接改状态。

## 5. 阶段契约

| 阶段 | 输入 | 输出 | 执行方 |
|---|---|---|---|
| `plan` | 需求 + 偏好 | 计划 JSON（含实现/审查厂商选择） | 调度模型 |
| `implement` | 需求 + 计划 | 完整文件集合 + diff | 实现厂商 |
| `review` | 需求 + 计划 + 固定 SHA 的文件 | 审查 JSON（`approved` + findings） | 审查厂商 |
| `test` | 集成后的工作树 | 测试报告 | 本地执行 |
| `summarize` | 前四阶段的证据 | 结论文本 | 本地确定性逻辑 |

两个约束：

1. `plan` 输出的实现厂商与审查厂商必须不同，否则计划被拒——这个校验在代码里，
   不依赖提示词自觉。
2. `test` 与 `summarize` 不调用模型。测试用本地执行是事实来源，总结是对已有证据的
   重述，再调一次模型只会引入新的不确定性和费用。

## 6. 适配器契约

适配器只做一件事：**给定结构化输入，返回结构化输出**。

```python
@dataclass(frozen=True)
class StepRequest:
    stage: str
    prompt: str
    schema: dict[str, object]      # JSON Schema，适配器必须校验
    context: dict[str, object]     # 含 revision、plan 等
    attempt: int

@dataclass(frozen=True)
class StepResult:
    outcome: str                              # ok / failed / rate_limited / ...
    data: dict[str, object] = field(default_factory=dict)
    summary: str = ""
    usage: dict[str, object] = field(default_factory=dict)
    cost_usd: float | None = None             # None = 未知，不是 0
    provider: str = ""
    model: str = ""

class Adapter(Protocol):
    id: str
    def capabilities(self) -> Capabilities: ...
    def run(self, request: StepRequest) -> StepResult: ...
```

设计要点：**文件落盘不是适配器的职责**。适配器返回文件内容，内核负责校验路径、
写工作树、提交并固定 SHA。这样任何新厂商的接入都不会碰到文件系统，也不会绕过校验。

内核不得出现任何具体厂商名。厂商名只存在于装配层与适配器实现中，用测试固化这条规则。

### 6.1 两种后端形态

适配器只管契约，不管后端是什么。同一套契约支持两种实现：

| 形态 | 配置 | 凭据在哪 | 说明 |
|---|---|---|---|
| `http` | `base_url` + `api_key` + `model` | 用户配置里 | 任何兼容接口 |
| `cli` | `command` + 参数模板 + 输出解析 | **完全不在本项目里** | 本机已安装、已登录的命令行工具 |

`cli` 形态是本项目最想要的接法，因为它把凭据留在了原工具手里：

```python
# 示意：配置里只有用户自己填的命令，仓库中不含任何厂商字面量
{"backend": "cli",
 "command": ["/path/to/your/tool", "--json", "--print"],
 "timeout": 600,
 "result_format": "json"}
```

内核做的事只有三件：把 `StepRequest` 写进子进程的标准输入、读它的标准输出、
按 `schema` 校验结果。它**不读取**该工具的凭据文件、**不复制**环境变量、
**不解析**它的登录状态。

这样「自带端点」在架构上是字面成立的：能不能跑、用谁的额度，完全由用户配置的
那一条命令决定。仓库不需要知道，也不该知道。

### 6.2 凭据模型

- 凭据只从进程环境或用户本地文件读取，**永不写入数据库、事件日志、产物或错误信息**
- 错误信息回传前做过滤：不原样回显可能含凭据的原始输出
- `cli` 形态下，内核与凭据零接触
- 不代管、不同步、不上传；不做**跨用户**池化与账号共享
  （同一用户配置多个端点不属于此列）

## 7. 失败语义

失败不重试到成功，而是分类保留：

| 结果 | 含义 | 后续 |
|---|---|---|
| `rate_limited` | 厂商限流 | 记录 `retry_after`，到期后可重试 |
| `quota_exhausted` | 额度用尽 | 停止，不换账号、不切计费 |
| `auth_required` | 未登录或凭据失效 | 停止，等人工处理 |
| `timed_out` | 超出阶段时限 | 停止，需显式恢复 |
| `policy_blocked` | 被策略拒绝 | 停止，需人工确认 |
| `failed` | 其他失败 | 停止，记录摘要 |

关键取舍：**不自动兜底**。自动换厂商或换计费方式会让「这次任务花了多少钱、用了谁」
变得不可知，而这个信息正是审计的前提。

## 8. 隔离与执行

- 每个任务一个独立工作树，从基线提交检出
- 实现阶段写入后立即提交，得到固定的 `revision`
- 审查读取的是 `revision` 处的文件，不是当前工作区
- 测试在工作树内运行，且在受限环境中：限制网络、限制可写路径、限制可执行文件

文件集合在使用前校验：相对路径、无路径穿越、无隐藏文件、扩展名白名单、总量上限。
校验失败即失败，不做「尽力而为」的清洗。

## 9. 审批模型

审批不是「允许这个 agent 继续」，而是**绑定到一次具体操作**：

1. 系统生成 `operation`（人类可读描述）与 `operation_digest`（描述 + 上下文的摘要）
2. 用户看到两者，回传**同一个** digest
3. digest 不匹配 → 409
4. 期间 `revision` 变了 → 审批失效 → 409

这防止了「批准时看到的是 A，执行时变成了 B」。digest 的作用不是加密，是**不可悄悄替换**。

## 10. 配置与审计

配置不是可变全局变量，而是带版本的对象：

- 每次更新需要携带 `base_revision`，不匹配即拒绝（乐观并发控制）
- 每次变更记录审计事件
- 新任务在创建时保存**不可变快照**，后续改配置不影响已存在的任务

这条对可复现性很重要：否则三个月后回看一个任务，无法知道它当时按什么策略执行。

## 11. 安全边界

- 只监听 `127.0.0.1`
- 校验 `Host` 头必须是回环地址或 `localhost`（防 DNS rebinding）
- 拒绝带 `Origin` 的请求（防浏览器跨站调用）
- 请求体有大小上限，拒绝分块传输

**已知缺口**：当前没有请求认证。loopback + Host/Origin 校验能挡住浏览器和远程主机，
但挡不住本机上的其他进程。在加入 token 之前，不要把它暴露到任何共享网络。

## 12. 扩展点

| 想做的事 | 正确位置 | 不该做的事 |
|---|---|---|
| 接入新厂商 | 新增 `Adapter` 实现 + 注册 | 改内核、加厂商分支 |
| 换搜索后端 | 替换 `search` 实现 | 让编排层知道索引细节 |
| 支持新平台沙箱 | 新增 `Sandbox` 实现 | 在业务逻辑里写平台判断 |
| 增加阶段 | **不建议** | 直接改 `STAGES` 而不改失败语义与证据链 |

## 13. 已知缺口

诚实列出，避免使用者误判成熟度：

- 没有库结构迁移机制，升级会破坏已有数据库
- 没有请求认证
- 沙箱只有 macOS 后端
- 没有代码库检索，规划阶段依赖模型对项目的猜测
- 成本对按量计费端点有效；端点不返回用量时只能记为「未知」
